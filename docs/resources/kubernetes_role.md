# portainer_kubernetes_role (Resource)

The `portainer_kubernetes_role` resource allows you to deploy one-off Kubernetes `Role` workloads into a specified namespace on a Kubernetes environment (endpoint) managed via Portainer.

---

## Example Usage
### Create Kubernetes Role from YAML
```hcl
resource "portainer_kubernetes_role" "example" {
  endpoint_id = 4
  namespace   = "default"
  manifest    = file("${path.module}/role.yaml")
}
```

## Lifecycle & Behavior
The Role is created via the Portainer Kubernetes API.

A change of `manifest` updates the existing object in place (a JSON merge patch), so a Deployment rolls out and a Service keeps its cluster IP; fields removed from the manifest are removed from the object. The object is deleted and created again only when it cannot be changed in place: another `metadata.name` or kind, another `namespace`, or a field Kubernetes does not allow to change (for example a Job's pod template or a Deployment's selector).

To update the Role (e.g. name, image), simply modify the manifest and re-apply:

```sh
terraform apply
```

To remove the role:
```sh
terraform destroy
```

**Drift detection.** On refresh, the fields set in `manifest` are compared with the live object: a value changed outside Terraform shows up in the plan, as the drifted fields with their live values, and the next apply puts the manifest back. Fields Kubernetes adds itself (status, defaults, `resourceVersion`) and canonical quantities (`500m` for `0.5`) are not drift. Fields the manifest does not set are not managed, so a key added outside Terraform is not reported.

## Schema

### Required

- `endpoint_id` (Number) Identifier of the Portainer Kubernetes environment (endpoint) where the Role is managed. Changing this value forces resource recreation.
- `manifest` (String) Raw YAML or JSON manifest defining the Kubernetes Role.
- `namespace` (String) Kubernetes namespace in which the Role is created.

### Read-Only

- `id` (String) Identifier of the resource.

## Notes on Arguments and Attributes

- `id`: ID in the format endpoint_id:namespace:role:name.

## Import

Kubernetes Role resources can be imported using the composite ID `endpointID:namespace:name`:

```shell
terraform import portainer_kubernetes_role.example 1:default:my-role
```

After import, set the `manifest` field in config to match the live object — Read only confirms the resource exists and restores identity fields, it does not reconstruct the manifest. If `manifest` is left blank after import, the next `terraform apply` treats the configured manifest as a change and updates the live object in place to match it.

### Import by identity

Terraform 1.12 and later can also import by resource identity: `endpoint_id`, `namespace` and `name`, the parts of the import ID, in an `import` block. The ID string above keeps working.

```hcl
import {
  to       = portainer_kubernetes_role.example
  identity = {
    endpoint_id = 1
    namespace   = "default"
    name        = "my-object"
  }
}
```

As with the ID, `manifest` is not read back by the import. `terraform query` (Terraform 1.14+) with the [`portainer_kubernetes_role` list resource](../list-resources/kubernetes_role.md) finds the objects to import and, with `include_resource = true`, fills `manifest` from the live object, so `terraform query -generate-config-out=generated.tf` writes a usable configuration. The identity is stored in the state from v3.1.0 on and follows an in-place rename or namespace change; state written by v3.0.0 gets it on the next refresh, without a plan change. OpenTofu supports neither resource identity nor list resources; it keeps importing by ID.
